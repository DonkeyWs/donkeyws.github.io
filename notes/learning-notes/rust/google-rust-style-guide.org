本文档是谷歌公司关于 Rust 编程语言使用的风格指南。在本文语境中，“风格”的范畴不止限于代码格式，还涵盖了应用程序接口（API）与实现设计的相关指导规范。

Rust 被应用在诸多场景中，包括[[https://opensource.google/documentation/reference/glossary#google3][google3]]、Android、ChromeOS、Fuchsia 以及 Chrome，我们希望谷歌内部的 Rust 代码在各个代码库内部及跨代码库之间的使用都能保持一致。除了让 Rust 代码实现统一外，风格规范还有助于确立一套质量标准。

** 背景

*** 范围

本指南中概述的规则当前的适用范围：
- 在 Android、Chromium 及其他代码库中：本风格指南是结合其他代码库的需求制定的，相关代码库计划开始采用本指南。这些代码库可能会针对本指南的执行严格程度制定各自的规则。随着这些代码库逐步采用本指南，此处将补充更多相关信息。

*** 风格指南的目标

总体而言，我们制定这份文档的原因与制定 [[https://google.github.io/styleguide/cppguide.html#Goals][C++ 风格指南]]的原因相同。

大多数风格规则均源于以下列出的一个或多个目标。

- *代码风格规则应优先考虑可读性和可维护性，而非可写性*

  #+begin_example
    我们期望代码能够长期留存，并且从长远来看，如果代码风格规则能提升可读性，那么在编写代码时多付出一点努力是值得的。
  #+end_example
- *代码风格规则应优先考虑更好的自动化实现*

  #+begin_example
    在谷歌，大规模变更（LSCs）十分常见，而一致性有助于让大规模变更的执行变得更轻松。
  #+end_example
- *样式规则应尽可能与更广泛的 Rust 生态系统保持一致*

  #+begin_example
    更广泛的 Rust 生态系统在风格上已经具备了相当不错的一致性，我们应尽可能依托这一特点，减少意外情况，同时也能降低学习 Google Rust 风格的工作量。
  #+end_example
- *代码风格规则应切实发挥作用*

  #+begin_example
    谷歌的每一位Rust开发人员和评审人员都必须牢记这些风格规则：因此，我们应谨慎纳入那些能带来切实益处的规则。
  #+end_example
- *风格规则有助于避免无关紧要的风格分歧*

  #+begin_example
    在很多情况下，理智的人可能会对某种风格持有不同看法，而且我们预计这种分歧会在代码审查（CL）中频繁出现。制定风格规则有助于避免每次都重新讨论这一问题。此类规则中，若没有其他益处，则应尽量少制定。
  #+end_example
